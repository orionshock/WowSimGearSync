IMPLEMENTATION
EquipmentInspector.lua owns one lazily created hidden GameTooltip. Each scan
clears lines, calls SetInventoryItem("player",slotId), requires hasItem and an
identical decoded tooltip/link payload, scans all FontString regions, then hides
it. Error/uncached/stale data cannot reuse the previous item's upgrade progress.
Only the client-supplied localized ITEM_UPGRADE_TOOLTIP_FORMAT is compiled;
no English fallback. %d and positional %1$d/%2$d work; color markers are removed.
Two consistent integer captures establish current>=0, maximum>0, current<=max.
Remaining=max-current. Conflicting/invalid lines stay UNKNOWN. A valid line
establishes eligibility even at 0/max. Task 009 runtime confirmation establishes
that eligible items always show this line: a successfully populated, identity-
verified tooltip without one establishes upgradeEligibility=KNOWN false and
upgradeState=NOT_UPGRADEABLE; progress fields and comparison are NOT_APPLICABLE.
Item 95757 is a confirmed example, not a hardcoded exception. Empty, failed,
stale, and inconsistent tooltips remain UNKNOWN. Ownership is renewed before
each inspection so probe and complete scans use the same tooltip lifecycle.

Observation fields: upgradeEligibility,upgradeStep,upgradeMaximum,
upgradeRemaining,upgradeState,tinker. Known observations include method source.
Upgrade states: FULLY_UPGRADED,PARTIALLY_UPGRADED,UNUPGRADED; uncertain observations
use UNKNOWN. Maximum-upgrade comparison ignores exported upgradeStep. Known
current maximum can differ from two. Wrong target item still blocks all
modification MATCH claims. Ring/trinket logic and link decoder are unchanged.
Settings remain db.profile; builds db.char; SavedVariables stays disabled.
