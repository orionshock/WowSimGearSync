compact badges and player-facing tooltip translation. No scanner
or comparator logic is copied. Opening calls the existing scanner and comparator
once; Render binds their exact targets, snapshot slots, differences and assignment
objects. Empty/selected builds share the same 16 reusable buttons. Import sends an
AceEvent message after saving; visible paper dolls refresh immediately.

use the authoritative
EquipmentSlots tokens with GetInventorySlotInfo for empty-slot textures.

Plain slot buttons have no click, drag, item-use or secure equipment handlers.

Normal tooltips show target/current names and concise applicable-step statuses.
Upgrade progress includes current/maximum and remaining upgrades. Debug mode
appends raw states, observation sources/reasons and resolved inventory assignment. Resolved ring and
trinket physical slots are taken directly from currentPosition/currentSlotId;
assignment labels distinguish inferred pairing from observed inventory data.

TASK 013: SLOT STATUS AND WAIST BUCKLE
Colored full-word states beside each icon appear in this order: Equipped,
Upgraded, Gemmed, Enchant/Buckle, Tinker, Reforged (only applicable steps).
Green means matched, amber means pending, red means wrong/missing item,
and blue means unknown. Missing/pending steps have a leading !; matched steps
have no symbol. Words are comma-separated and wrap within each slot's column.
Adjacent slot names are removed; names remain in tooltips. The center contains
only a small hover hint. Bottom counts, quality borders and disabled Equip remain. Icon corners stay clear.

Buckle requirement is implied only by a positive target gems[3] at waist (export
position 8, inventory 6). A populated third observed gem proves the implied socket
is present. Otherwise the scanner uses C_Item.GetItemNumAddedSockets(equippedLink)
only after C_Item.GetItemInfo returns cached item information. Local generated
ItemDocumentation.lua:572-584 documents itemInfo -> socketCount:number.
Positive added sockets mean present; zero means missing. API failure/unavailable
data stays UNKNOWN. An empty third gem alone never proves a missing buckle.
No hardcoded belt/socket database or tooltip-text guess is used.

The third-gem rule is an addon policy/inference, not identification of a buckle
enchantment. An empty added socket counts as buckle present but may still need a
gem. Added socket API runtime availability and equipped-link semantics need
confirmation on this MoP client; generated shared documentation is source
evidence, not live verification. If unavailable, empty-third-position belts stay
UNKNOWN. Wrong items block buckle matches. Gems and buckle are separate steps,
so both can contribute to configuration differences.
