Modules and contracts
EquipmentInventory enriches the scanner snapshot and scans bags 0..NUM_BAG_SLOTS.
Candidates retain exact location, GUID when available, full decoded link payload,
lock state, equipLoc and known gem/enchant/reforge observations. Missing/corrupt
links and uncached metadata block candidates; only empty general bag slots are
used for an off-hand removal. No bank, item requests or ongoing polling.
EquipmentPlanner returns operations, missing, blocked and comparator assignments.
It reserves correctly equipped instances first, including swapped ring/trinket
assignments. For remaining identical IDs it considers distinct assignments,
minimizing known gem/enchant/reforge mismatches (unknown observations break ties
against fully observed matches). Existing correct items are never replaced solely
to improve modifications. One physical GUID/location cannot serve two targets.
Without GUID, a unique full payload plus source movement is required; identical
unidentifiable copies are blocked. Targets are never substituted by another ID.
Empty targets are left alone except off-hand removal needed by an available
2H main-hand target. Actual known Titans Grip permits 2H pair planning; native
CursorCanGoInSlot remains the final authority for class/weapon restrictions.
A current 2H main hand must be replaced before off-hand work becomes actionable.

Execution and verification
EquipmentExecution runs synchronously from the Equip button click, out of combat.
It checks cursor, locks and source identity again, picks up the exact source,
checks native slot acceptance and places it. A displaced item returns to the
source location where possible. It never clears a pre-existing cursor item.
If a displaced item cannot return (for example specialty bag restrictions), the
cursor remains user-owned and requires manual placement. Native bind confirmations
and protection rules are not suppressed or bypassed.
EquipmentActions submits ONE transaction per click. No equipment function runs
from a timer or event. Source/target changes are verified by GUID, or conservative
unique-payload/source-movement evidence, on equipment/bag/lock events. A function
return is not success. Replanning follows observed changes; double clicks are
blocked while pending and briefly debounced. Four seconds without verification
produces a fault. The next click rescans only; a subsequent click retries.
A wrong instance or unexpected destination change stops work. Combat and occupied
cursor block new operations. Closing the doll still allows pending verification;
otherwise hidden UI performs no ongoing inventory scans. Refreshes are coalesced.

Hardware/security limitations requiring live validation
Local source establishes the native cursor transaction, not an unlimited secure
batch or a universal hardware-event contract for addon Lua. The ordinary button
issues one transaction from its hardware OnClick; actual MoP protected-action
behavior must be tested in game. If the client refuses it, that refusal is reported
and no workaround is attempted. SecureActionButton item/name lookup alone cannot
guarantee the chosen duplicate instance/destination. Multi-item batching is not
claimed. Native errors, bind prompts, latency, full/specialty bags and weapon
restrictions can require manual intervention. A delayed unverified change may
later become visible on a rescan; it never causes another automatic action.
No item modification, currency spending or build/name/database writes occur.
SavedVariables remains disabled. Existing settings/build scopes are unchanged.
